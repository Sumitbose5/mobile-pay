# CoinHub

A transaction-safe digital wallet. Users add money, send and request money, and see a full history. The engineering focus is financial correctness: no double-spending under concurrent requests, no duplicate payments on retries, and a double-entry ledger that always balances.

**Stack:** React + TypeScript + Vite + Tailwind + shadcn/ui (client) | Express + TypeScript + Drizzle ORM + PostgreSQL on Neon + Redis + BullMQ (server).

```
coinhub/
  client/   React app (Vite, Tailwind v4, shadcn/ui, TanStack Query, React Router)
  server/   Express API (Drizzle, Zod, pino) - controller > service > repository
  docs/     ERD and architecture decision records
  docker-compose.yml   local Postgres, Redis, Mailpit
```

## Quick start

```bash
npm install
cp server/.env.example server/.env     # then edit secrets (openssl rand -hex 32)
cp client/.env.example client/.env
docker compose up -d                    # Postgres, Redis, Mailpit (skip if using Neon)
npm run db:migrate
npm run db:seed
npm run dev                             # API :4000, web :5173
```

Open http://localhost:5173. The home page shows a live status check for the API, PostgreSQL and Redis. Mailpit inbox: http://localhost:8025.

Seeded accounts (development only): `admin@coinhub.local` / `Admin@12345`, `sumit@coinhub.local` and `rahul@coinhub.local` / `Demo@12345`.

## Using Neon

Create a Neon project and put two connection strings in `server/.env`:

| Variable | Use | Neon string |
|----------|-----|-------------|
| `DATABASE_URL` | App runtime | pooled (host contains `-pooler`) |
| `DATABASE_URL_DIRECT` | Migrations | direct (no `-pooler`) |

Set `DATABASE_SSL=true`. The app uses `pg` over TCP because money transfers need interactive transactions with `FOR UPDATE`, which the Neon HTTP driver does not support.

## Database

Schema lives in `server/src/db/schema/` (one file per table). Migrations in `server/src/db/migrations/`:

- `0000_init_schema.sql` generated by drizzle-kit (tables, enums, CHECKs, indexes)
- `0001_db_guards.sql` hand-written triggers (append-only ledger and audit log, status state machine, double-entry balance)
- `0002_single_system_wallet.sql` exactly one platform clearing wallet

See `docs/erd.md` for the diagram and `docs/adr/` for the reasoning behind money as bigint, locking, the outbox, cookie auth and database-level guards.

## Phase 1: authentication and users

Implemented: register, email verification (wallet created in the same DB transaction), login, logout, refresh-token
rotation with reuse detection, forgot/reset password, change password, session list and revoke, profile and
notification preferences, RBAC, CSRF, rate limiting and audit logging.

| Endpoint | Notes |
|----------|-------|
| `GET /api/v1/auth/csrf` | Sets the `csrf_token` cookie; echo it in the `x-csrf-token` header on every POST/PATCH/DELETE |
| `POST /auth/register`, `/auth/verify-email`, `/auth/resend-verification` | Responses never reveal whether an email exists |
| `POST /auth/login`, `/auth/refresh`, `/auth/logout` | HttpOnly cookies; refresh token rotates on every use |
| `POST /auth/forgot-password`, `/auth/reset-password`, `/auth/change-password` | Reset tokens are single use (Redis, 30 min) |
| `GET /auth/sessions`, `DELETE /auth/sessions/:id` | One entry per signed-in device |
| `GET/PATCH /users/me`, `GET/PATCH /users/me/notification-preferences` | |
| `GET /admin/ping` | Admin-only; proves server-side RBAC (real admin routes arrive in Phase 7) |

Security decisions worth knowing:
- Access JWT (15 min) and refresh token (7 days, opaque, stored as a SHA-256 hash) live in HttpOnly, SameSite=Strict cookies. The refresh cookie is scoped to `/api/v1/auth`.
- Replaying a rotated refresh token outside a 10 s grace window revokes the whole session family and raises a CRITICAL audit event. Inside the window it is treated as a racing browser tab.
- Rate limits (Redis-backed): login 5 failed attempts / 15 min per email+IP, forgot-password 3 / hour, register 10 / hour, 100 requests / min per IP globally.
- Email is sent in-process for now; Phase 5 moves it behind a BullMQ `send-email` job without changing callers.
- Access tokens are verified statelessly, so a role or status change takes effect within 15 minutes or at next refresh (refresh re-checks account status).

Tests: `npm test` runs 40 tests; `server/tests/auth.test.ts` covers the full flow, CSRF, token reuse, the concurrent-refresh race and RBAC. They need Postgres (`coinhub_test`) and Redis.

## Phase 2: wallet, transaction PIN, add money

| Endpoint | Notes |
|----------|-------|
| `GET /wallet`, `GET /wallet/balance` | Read straight from PostgreSQL; amounts are integer-paise strings |
| `POST /users/me/pin`, `PUT /users/me/pin` | Set needs the account password; change needs the current PIN. 3 wrong PINs lock entry for 30 minutes (Redis) |
| `POST /wallet/add-money` | Requires a PIN and an `Idempotency-Key` header. Creates a gateway order; no money moves yet |
| `POST /payments/webhook` | Gateway callback, HMAC-signed (`x-gateway-signature`, `x-gateway-timestamp`). Idempotent |
| `POST /payments/simulator/:orderId/complete` | Stand-in for the gateway checkout page (disabled in production) |
| `GET /payments/orders/:id` | Owner only |

How money moves: `applyTransfer()` locks both wallets in id order, validates, writes the transaction, both balances and
the two ledger entries. Add money debits the platform clearing wallet and credits the user. See ADR 0006.

`npm test` now runs 60 tests. `server/tests/wallet.test.ts` includes: the same signed webhook delivered 20 times in
parallel credits once; 10 parallel add-money requests with one idempotency key create one order; a wallet frozen
between order and payment is not credited; and the ledger is checked to reconcile after the money tests.

Still to come for the PIN: an emailed "forgot PIN" reset flow.

## Phase 3: send money and transactions

| Endpoint | Notes |
|----------|-------|
| `POST /wallet/send` | `{ receiverEmail \| receiverId, amount, note?, pin }` with an `Idempotency-Key` header |
| `GET /wallet/recipients/lookup?email=` | Confirms who will be paid (name only); rate limited |
| `GET /transactions` | Filters: `q`, `direction` (SENT, RECEIVED, ADDED, WITHDRAWN), `type`, `status`, `from`, `to`, `minAmount`, `maxAmount`; `limit` and opaque `cursor` |
| `GET /transactions/:id` | Both parties, notes, timestamps, your balance before and after, failure reason. Not yours: 404 |

Send money flow: validate, resolve recipient, verify PIN (lockout), check limits, then one database transaction:
`applyTransfer()` locks both wallets in id order, re-checks wallet status, recipient cap and the **daily limit under the
lock**, moves the money, writes two ledger entries and two outbox events. Business refusals are kept as FAILED history rows.

Idempotency refinements: only successful responses are remembered (a wrong PIN or insufficient balance releases the key
so the user can fix it and retry the same key), and the PIN is excluded from the request hash.

`npm test` now runs 85 tests. `transfers.test.ts` covers the headline guarantees: 10 parallel spends of a full balance
let exactly one through; 50 parallel sends of Rs 100 from Rs 1,000 let exactly 10 through and the balance never goes
negative; 40 simultaneous A->B and B->A transfers do not deadlock and conserve total money; parallel sends cannot jointly
exceed the daily limit; and the ledger reconciles after each scenario. See ADR 0007 for the history design and the
measured query performance.

## Phase 4: financial correctness

- `npm run reconcile` checks the whole system and exits 1 if any invariant is violated (balance vs ledger, unbroken ledger
  chains, balanced transactions, SUCCESS transactions match their entries, no negative wallets, nothing stuck, money conserved).
- `POST /admin/reconciliation/run` and `GET /admin/reconciliation` (admin only) run and read the same report.
- `POST /admin/transactions/:id/reverse` `{ reason }` (admin only) posts a linked reversal. At most once, never edits history,
  refuses if the recipient already spent the money.
- Money transactions now go through `withTransaction()`: lock timeout (`LOCK_TIMEOUT_MS`, default 5000) so a held lock gives a
  fast `503 SERVICE_BUSY`, and bounded retry on deadlock or serialization failure.
- Hardening found by failure injection: pool clients now have an error listener, so a database connection dying mid-transaction
  rolls back cleanly instead of crashing the process.

`npm test` now runs 105 tests. New suites: `reliability.test.ts` (forced deadlock retried, lock timeout to 503, rollback after a
crash, connection killed before COMMIT, database refuses a one-sided ledger), `reversal.test.ts` (6 parallel reversals reverse
once, cannot create money, works on frozen wallets) and `reconciliation.test.ts` (each invariant is shown to catch deliberately
corrupted data). See ADR 0008.

## Phase 5: Redis, background jobs, notifications

Run the worker alongside the API (`npm run dev` starts both; in production run `npm run start:worker` as its own service). It needs
the same `REDIS_URL` and `QUEUE_PREFIX` as the API.

| What | How |
|------|-----|
| Outbox dispatcher | Turns committed `outbox_events` rows into jobs; `FOR UPDATE SKIP LOCKED`, at-least-once, idempotent consumers |
| `send-email` | 5 attempts, exponential backoff (`EMAIL_BACKOFF_MS`); failures end in BullMQ's failed set (dead letter) |
| `send-notification` | Creates the in-app notification; unique dedupe key makes redelivery harmless |
| Maintenance | `cleanup-idempotency-keys` (hourly), `expire-payment-orders` (5 min), `cleanup-refresh-tokens` (daily), `reconcile-ledger` (daily; alerts admins on failure) |
| `GET /notifications`, `/notifications/unread-count`, `PATCH /notifications/:id/read`, `POST /notifications/read-all` | Cursor-paginated; unread count cached in Redis and invalidated on change |
| `GET /transactions/summary` | This month's money in and out, cached 60 s, invalidated when money moves |
| `GET /admin/queues` | Read-only Bull Board for admins |

Caching covers display data only (`/users/me`, monthly summary, unread count). Balances, limits and PIN state used in decisions
always come from PostgreSQL. See ADR 0009.

Mail: with no SMTP server running (no Mailpit), email jobs retry and then land in the failed set; the app keeps working.
Start Mailpit with `docker compose up -d` to see the emails at http://localhost:8025.

`npm test` now runs 125 tests; `jobs.test.ts` runs against real Redis and BullMQ: outbox to notifications and email,
preferences, idempotent redelivery, three dispatchers racing (each event handled once), SMTP retry with backoff, dead-lettering,
cache invalidation, maintenance jobs, the reconciliation alert and schedule registration.

## Phase 6: beneficiaries, payment requests, withdrawals, statements

| Endpoint | Notes |
|----------|-------|
| `GET/POST /beneficiaries`, `PATCH/DELETE /beneficiaries/:id` | Adding needs the PIN; max 50; soft delete |
| `POST /payment-requests`, `GET /payment-requests?box=received\|sent`, `GET /payment-requests/:id` | Max 20 open; expire after 7 days |
| `POST /payment-requests/:id/pay` | PIN + `Idempotency-Key`; goes through the normal send path |
| `POST /payment-requests/:id/reject` (payer), `/cancel` (requester) | 409 `REQUEST_NOT_PENDING` if already settled |
| `GET/POST /bank-accounts`, `DELETE /bank-accounts/:id` | UPI or bank account; only masked values stored; max 5 |
| `POST /wallet/withdraw` | PIN + `Idempotency-Key`; funds held now, payout job settles; failure refunds automatically |
| `POST /transactions/export`, `GET /transactions/export/:id`, `.../download` | CSV statement built by the worker |
| `POST /users/me/pin/reset-request`, `/users/me/pin/reset` | Forgot PIN: password, then emailed link |

Try the refund path: add a payout account whose holder name contains "fail", withdraw to it, and watch the money come back.
New background jobs: `process-payout`, `generate-report`, `cleanup-expired-requests` (every 5 minutes). See ADR 0010.

`npm test` now runs 160 tests. Highlights: pay vs reject and pay vs cancel at the same instant end exactly one way; 8 parallel
payments of one request transfer once; 25 parallel request creations yield exactly 20; 10 parallel full-balance withdrawals let
one through; a payout settles at most once however often the job runs; a rejected payout refunds through a linked reversal and
reconciliation accepts exactly that case; the CSV excludes other people's failed attempts and neutralises formulas.

## Phase 7: admin console

Create an administrator (there is no public way to become one): `npm run admin:create -- you@example.com "Your Name" 'A-Strong-Passw0rd'`
(the seed also creates `admin@coinhub.local`). Then open `/admin` (an "Admin" button appears in the app header).

| Endpoint | Notes |
|----------|-------|
| `GET /admin/stats` | Users, wallet totals, today's volumes and failure rate, alerts, last reconciliation; cached 60 s |
| `GET /admin/users`, `GET /admin/users/:id` | Search, filter, paginate; detail shows wallet, sessions, recent transactions and audit (viewing is audited) |
| `POST /admin/users/:id/freeze` `{ reason }`, `/unfreeze`, `/force-logout` | Freeze takes effect immediately, even for payments in flight; admins cannot be frozen |
| `GET /admin/transactions`, `GET /admin/transactions/:id` | All statuses incl. other people's failed attempts; detail has ledger entries, reversal links, audit trail |
| `POST /admin/transactions/:id/reverse` | From Phase 4; now available from the transaction page |
| `GET /admin/audit-logs`, `GET /admin/suspicious` | Filter by user, action, severity, date; keyset-paginated |
| `GET /admin/reconciliation`, `POST /admin/reconciliation/run` | Latest report and run-now |
| `GET /admin/queues` | Read-only job queue dashboard |

Admin access is checked against the database on every request, so demoting or suspending an administrator takes effect immediately
rather than when their 15-minute token expires. Fraud rules (velocity, large amount, new-payee-large) flag for review and never block a
payment; thresholds are in `system_settings` (`fraud.*`). See ADR 0011.

`npm test` now runs 178 tests. `admin.test.ts` covers: demotion and suspension taking effect on a still-valid token; stats deltas; user
search and detail; freeze blocking every way of moving money while login and history still work; a freeze landing in the middle of
30 parallel payments (each payment either completes first or is refused, nothing half-done, ledger reconciles, and all later payments
are refused); transaction and audit filters with gap-free paging; the three fraud rules flagging without blocking; and the
`admin:create` script.
