# ADR 0010: Settle requests inside the money transaction, hold withdrawals, export in the background

**Status:** accepted (Phase 6)

**Decisions.**
1. **Paying a request reuses the send-money path.** `sendMoney()` accepts `before` and `after` hooks that run inside the money
   transaction. `before` locks the request row and re-checks it is still open; `after` flips it to PAID and links the transaction.
   PIN, limits, wallet checks, idempotency and the ledger are therefore identical to a normal send, and the request and the money
   commit together or not at all. Pay, reject, cancel and expire all lock the same row, so a request ends exactly one way. A cheap
   pre-check stops an already-settled request from spending the user's PIN attempts.
2. **Open-request cap under concurrency.** Creating a request takes a per-user advisory lock before counting, so 25 parallel
   creations produce exactly 20 requests.
3. **Withdrawals hold funds, then settle asynchronously.** The debit moves the money to the platform clearing wallet immediately
   and leaves the transaction PROCESSING; a `WITHDRAWAL_REQUESTED` outbox event (same commit) makes the dispatcher enqueue the
   payout job. The job locks the transaction and only acts on PROCESSING, so retries and duplicates do nothing. Success completes it;
   rejection marks it FAILED and posts a linked REVERSAL (the unique reversal link allows one refund). In flight, the amount counts
   as money out and against the daily limit. The bank is simulated (holder name containing "fail" is rejected).
4. **Reconciliation understands refunds.** A FAILED withdrawal legitimately keeps its ledger entries when a successful linked
   reversal exists; any other FAILED/CANCELLED/PENDING transaction with entries is still a violation.
5. **Statements are generated by a worker.** The request returns 202 and a report id; the worker builds the CSV with the same
   visibility rules as the history screen and stores it in Redis for an hour; the owner polls and downloads. Free-text cells are
   neutralised against spreadsheet formula injection (a leading `=`, `+`, `-`, `@`, tab or CR gets an apostrophe), but numeric
   columns are written as plain numbers: guarding them turned `-250.50` into text and broke totals.
6. **Beneficiaries and payout accounts need the PIN to add** and are soft-deleted. Only masked identifiers are stored for payout
   accounts (UPI `as***@bank`, account last 4 + IFSC); the full values are discarded after validation.
7. **Forgot PIN** needs a logged-in session AND the account password, then an emailed single-use link (30 minutes) bound to that
   user. Completing it clears any PIN lockout.

**Known limits.** Every add-money and withdrawal updates the single platform clearing wallet row, so those flows serialise on it.
That is fine at this scale; a production system would shard clearing accounts. Statements live in Redis (one hour) rather than
object storage. A real bank integration replaces `bankAccepts` and would add its own settlement reconciliation.
